# Research: Phase 7B.2 — Typography & Decoration Quality

> **Date:** 2026-03-16
> **Status:** Complete
> **Confidence:** HIGH — multiple sources verified, clear recommendation

---

## Problem Statement

Generated POD artwork has good illustration quality but typography/decorative text quality doesn't match the original design. The current model (`gemini-2.5-flash-image`) has ~80% text rendering accuracy and struggles with decorative typography styles (hand-lettered, vintage, script, etc.).

## Current Architecture

```
SynthesizedConcept (suggestedText, textStyle, textLayout)
    ↓
generateArtwork() — single prompt to gemini-2.5-flash-image
    ↓
AI generates BOTH illustration AND text in a single pass
    ↓
Text quality limited by model capabilities
```

**Root Cause:** All-in-one generation asks the model to be both an illustrator AND a typographer. AI models are inherently non-deterministic for glyph shapes — they "guess" letter forms instead of rendering fonts.

---

## Approaches Evaluated

### Approach 1: Model Upgrade (gemini-3-pro-image)

| Attribute | gemini-2.5-flash-image | gemini-3-pro-image |
|-----------|----------------------|-------------------|
| Text accuracy | ~80% | ~94% |
| Max resolution | 1024×1024 | 4096×4096 (4K) |
| Speed | ~3-5s | ~8-12s |
| Price | $0.039/image | $0.134/image (1K-2K), $0.24 (4K) |
| Reasoning | Standard | Built-in "thinking" mode |
| API ID | `gemini-2.5-flash-image` | `gemini-3-pro-image-preview` |

**Pros:**
- No architecture change needed — drop-in model swap
- 94% text accuracy is "production-ready for most text-heavy use cases"
- Better reasoning handles complex prompts
- Higher resolution for print quality

**Cons:**
- 3.4× more expensive ($0.134 vs $0.039)
- Still not 100% — ~6% error rate on text
- Slower (8-12s vs 3-5s)
- Decorative typography (hand-lettered, ornate) still AI-generated, not font-precise
- No free tier

**Verdict:** Quick win for significant improvement. Good for decorative text where exact glyph fidelity isn't critical. BUT doesn't solve the fundamental problem — AI still "draws" text instead of rendering fonts.

### Approach 2: Separate Text Overlay (Canvas API)

Generate illustration-only → overlay text programmatically in browser using real fonts.

**Architecture:**
```
generateArtwork() → illustration ONLY (no text in prompt)
    ↓
Canvas API + Google Fonts
    ↓
Load font file → measure text → render at high DPI → composite on illustration
    ↓
Export final image with precise typography
```

**Key Libraries:**
- **opentype.js** — Parse font files, get paths, SVG export. `font.getPath()` returns vector paths
- **Google Fonts** — Free commercial use (OFL/Apache), 1,600+ families
- **Canvas API** — Native browser, `fillText()`, `measureText()`, `textRendering` property
- **FontFace API** — Load fonts programmatically: `new FontFace("name", "url(x)").load()`

**For decorative effects:**
- Arched/curved text → opentype.js `getPath()` → transform path points along curve
- Text on path → SVG `<textPath>` element
- Effects (shadow, stroke, gradient) → Canvas shadow/stroke APIs or SVG filters

**Pros:**
- 100% accurate text — real fonts, deterministic rendering
- Vector-quality at any DPI
- Full control over kerning, ligatures, effects
- Free fonts (Google Fonts)
- No additional API cost

**Cons:**
- Complex implementation — needs text measurement, positioning, compositing
- Decorative styles limited to what CSS/Canvas can do (no hand-lettered AI magic)
- Text doesn't "integrate" into illustration naturally (sits on top)
- Must leave "space" for text in illustration (prompt engineering)
- Doesn't capture the aesthetic feel of truly decorative typography in original designs

**Verdict:** Best for clean typography (sans-serif, serif, monospace). NOT ideal for hand-lettered, artistic, or heavily integrated decorative text that's part of the illustration itself.

### Approach 3: Two-Pass AI Generation

Pass 1: Generate illustration-only → Pass 2: Edit/inpaint to add text.

**Architecture:**
```
Pass 1: generateArtwork() → illustration only
    ↓
Pass 2: Gemini image editing → "Add this text in this style"
    ↓
AI places text with context of existing illustration
```

**Pros:**
- Text integrates naturally with illustration
- Can leverage illustration context for placement
- Gemini supports conversational editing

**Cons:**
- Still AI-generated text → same glyph fidelity issues
- Two API calls = 2× cost
- Non-deterministic — may alter illustration
- No guaranteed improvement over single-pass

**Verdict:** Not recommended. Doubles cost without solving the core problem. Only useful for "textured text" where exact shapes don't matter.

### Approach 4: Hybrid — Model Upgrade + Selective Canvas Overlay

**Use the best tool for each job:**

```
OPTION A: "Decorative/Artistic text" → gemini-3-pro-image-preview
          (AI draws text AS PART of illustration, 94% accuracy)

OPTION B: "Clean/Professional text" → gemini-2.5-flash-image + Canvas overlay
          (AI draws illustration only, Canvas renders text precisely)

User/System decides based on textStyle from concept:
  "hand-lettered", "vintage", "script" → OPTION A (decorative = AI, higher model)
  "sans-serif", "serif", "clean", "bold" → OPTION B (clean = Canvas)
```

**Pros:**
- Best of both worlds — decorative + precise
- Cost optimization — only use expensive model when needed
- Fallback strategy — if AI text fails, retry with Canvas
- Progressive enhancement path

**Cons:**
- More complex codebase (two rendering paths)
- Need to classify text styles
- Visual consistency between two approaches

## Architecture Patterns

### Pattern 1: Model Selector (Recommended first step)
```typescript
function selectImageModel(textStyle: string): string {
  const decorativeStyles = ['hand-lettered', 'vintage', 'script', 'decorative', 
                            'retro', 'grunge', 'brush', 'calligraphy'];
  const isDecorative = decorativeStyles.some(s => 
    textStyle.toLowerCase().includes(s));
  return isDecorative 
    ? 'gemini-3-pro-image-preview'  // Better text rendering
    : 'gemini-2.5-flash-image';     // Faster, cheaper
}
```

### Pattern 2: Canvas Text Overlay (Phase 2)
```typescript
async function overlayText(
  illustrationDataUrl: string,
  text: { primary: string; secondary?: string; style: string; layout: string },
  font: { family: string; url: string }
): Promise<string> {
  // 1. Load font
  const fontFace = new FontFace(font.family, `url(${font.url})`);
  await fontFace.load();
  document.fonts.add(fontFace);
  
  // 2. Load illustration
  const img = await loadImage(illustrationDataUrl);
  
  // 3. Create high-DPI canvas
  const dpr = 2; // or window.devicePixelRatio
  const canvas = document.createElement('canvas');
  canvas.width = img.width * dpr;
  canvas.height = img.height * dpr;
  const ctx = canvas.getContext('2d')!;
  ctx.scale(dpr, dpr);
  
  // 4. Draw illustration
  ctx.drawImage(img, 0, 0, img.width, img.height);
  
  // 5. Render text with proper font
  ctx.font = `bold ${fontSize}px "${font.family}"`;
  ctx.textAlign = 'center';
  ctx.fillStyle = textColor;
  ctx.textRendering = 'optimizeLegibility';
  ctx.fillText(text.primary, img.width / 2, yPosition);
  
  // 6. Export
  return canvas.toDataURL('image/png');
}
```

## Don't Hand-Roll

- **Font shaping/kerning** — Use opentype.js or native Canvas API, not manual positioning
- **Font file loading** — Use FontFace API, not XHR
- **DPI conversion** — Use standard `canvas.width = cssWidth * (dpi/96)` pattern
- **Text measurement** — Use `ctx.measureText()` or `opentype.js` metrics

## Common Pitfalls

1. **Canvas blur at high DPI** — Must set canvas bitmap size to CSS size × devicePixelRatio and scale context
2. **Font not loaded before render** — Must await `FontFace.load()` or `document.fonts.ready`
3. **Cross-browser text hinting** — Safari/Chrome snap to whole pixels, Firefox to half pixels
4. **AI model omitting text area** — Prompt must explicitly tell model to leave space for text
5. **Google Fonts licensing** — OFL allows commercial use including POD, but font cannot be sold alone
6. **Gemini 3 Pro pricing gotcha** — No free tier, $0.134/image minimum, 4K is $0.24

## Recommended Strategy

### Phase 1 (Quick Win): Model Upgrade ← **START HERE**
- Swap `gemini-2.5-flash-image` → `gemini-3-pro-image-preview` for artwork generation
- Keep same architecture (single-pass, AI generates everything)
- Expected improvement: 80% → 94% text accuracy
- Cost increase: $0.039 → $0.134/image (~3.4×)
- Implementation: Change 1 line in `api.ts`
- **Add user setting** to choose quality tier (Fast/Quality)

### Phase 2 (If needed): Smart Model Selection
- Classify textStyle as decorative vs clean
- Route decorative → Pro, clean → Flash + Canvas overlay
- Requires opentype.js + Google Fonts integration
- More complex but cost-optimized

### Phase 3 (Future): Full Canvas Typography Pipeline
- Only implement if Phase 1 doesn't meet quality bar
- Requires significant architecture change
- Best for "studio-grade" typography control

## Key Decision Points

1. **Start with model upgrade** — simplest change, biggest impact (80→94% accuracy)
2. **Add quality tier toggle** — let user choose Fast (Flash) vs Quality (Pro)
3. **Evaluate results** — if 94% is enough for POD, stop here
4. **If not** → implement Canvas overlay for clean text styles
5. **NEVER** implement two-pass AI — cost doubles with minimal quality gain
